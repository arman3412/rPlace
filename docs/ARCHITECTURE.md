# Storage decision (before implementation)

| Approach                                         | Persistent canvas storage |               Placement writes | Join cost                              | Tradeoff                                                                                        |
| ------------------------------------------------ | ------------------------: | -----------------------------: | -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Events only                                      |                         0 |           wallet cooldown only | Replay all placements since deployment | Lowest transaction gas, but unbounded initial loading; third-party snapshots need proof/replay. |
| One slot per pixel, including author             |        up to 10,000 slots |               pixel + cooldown | Full-state read (320 KB minimum ABI)   | Simple, but expensive first writes, and ownership duplicates receipt data.                      |
| Ten RGB pixels per word + event authors (chosen) | up to 1,000 slots / 32 KB |         packed word + cooldown | One 32 KB contract call                | Bounded current-state loading, shared word initialization, history requires log access.         |
| Tightly contiguous 30,000-byte bitstream         |  938 slots / 30,016 bytes | sometimes two words + cooldown | ~30 KB call                            | Saves 6.2% capacity but colors straddling words cost a second SSTORE.                           |

Choose packed words before implementing: `uint256[1000]`, ten 24-bit lanes each, 16 unused bits. Store bitwise-inverted RGB: zero storage represents white. No 1,000-slot constructor initialization. Pixel id = y * 100 + x. Contract accepts id + uint24; ABI rejects out-of-range colors, contract rejects ids >= 10,000. All colors, including pure black and white, are exact.

Keep last placement timestamp per wallet in one mapping slot; no author, counter, timestamp per pixel, payment, owner/admin, proxy, token, or array of history entries. Emit indexed pixel id plus author and color. A pixel's current author and history come from ordered receipt logs, even if its color returns to white. One wallet's first placement writes a new cooldown slot; subsequent writes update the existing slot. A 60-second cooldown prevents a single wallet flooding but is not Sybil resistance.

## Read/synchronization protocol

The browser reads a packed snapshot at an explicit block two blocks behind head, never thousands of independent pixel calls. It decodes locally. Recent feed scans a bounded block window; per-pixel history uses indexed id, backward pagination, and adaptive subdivision on RPC range/response errors. A rare pixel may still require scanning many empty ranges: RPC providers do not expose an indexed “last event” query. No ownership is invented when a scan is incomplete.

Poll every four seconds. Before advancing, check the previous cursor's block hash; fetch logs in ascending bounded chunks through the new head-minus-two; verify the endpoint hash before applying; deduplicate by block hash + log index; apply in block/log order. On a detected reorganization, discard state and read a new snapshot. Cursor advancement happens only after all log chunks succeed. Initial/recovery reads are block-pinned. The UI distinguishes approval, broadcast/pending, receipt inclusion, and synchronized confirmation. A receipt is provisional until the chosen depth; the canvas only displays the confirmed event/snapshot. Two-block depth reduces reorg exposure but is not economic finality; deep reorgs are recoverable.

RPC providers are availability and data trust dependencies, as with ordinary Ethereum wallets. No centralized application backend is necessary. Independent users can choose another RPC and reproduce state from events or read contract storage. Strong proof verification would require a light client; ordinary JSON-RPC is not a cryptographic proof verifier. Historical receipts must remain accessible through an archive/log provider. State reads remain bounded regardless of placement count; historical reads grow with searched block span and matches. Never persist an unverified browser snapshot as authoritative.
